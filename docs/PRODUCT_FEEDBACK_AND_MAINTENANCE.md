# Cofound 产品反馈与集中维护

版本：Cofound Investment Office 1.2.3
能力包：0.12.0+codex.20260824

## 这项功能解决什么

团队成员不需要理解源码、Git 或发布流程。使用中遇到问题时，可以在本机网页填写一张简短反馈，也可以直接在自己的 Codex 中用自然语言提交。其本机 Codex 负责第一轮复现、定位和整理；安全摘要进入企业内部飞书多维表格，由唯一维护者逐条决定是否纳入正式改进。

网页反馈和正式产品迭代是两条不同的链。提交建议不等于代码已经修改；Codex 的本地试修也不等于团队版本已经更新。只有维护者在集中收件箱中选择“纳入改进”，系统才创建正式迭代任务。

## 用户流程

```text
团队成员遇到问题
        ↓
本机网页“问题反馈”或自然语言告诉 Codex
        ↓
先保存在本机，形成独立反馈编号
        ↓
本机 Codex 复现、定位、提出调整建议并做安全检查
        ↓
安全摘要自动同步到飞书“产品改进台账”
        ↓
维护者在本机“产品改进”收件箱逐条查看
        ↓
待补充 / 相似问题 / 暂缓 / 纳入改进
        ↓
“纳入改进”才生成正式 Codex 迭代任务
        ↓
维护者审核结果并完成正式本地版本
        ↓
处理状态回写飞书；提交人本机可刷新查看进度
```

## 团队成员看到什么

- “问题反馈 / Feedback”页面；
- 问题描述、期望结果、功能分类和影响程度；
- 本机保存状态与飞书发送状态分开显示；
- Codex 整理状态、诊断摘要、建议下一步和仍需补充的问题；
- 维护者的处理状态与回复；
- 发送失败时可以安全重试，本机内容不会因此丢失。

如果飞书尚未配置或暂时不可用，反馈仍保存在本机并进入待同步状态。产品不会为了“看起来成功”而把本机记录静默删除。

## 维护者看到什么

维护端自动识别为包含正式工程版本控制信息的主工作区。普通交付副本不会显示集中维护入口。

维护者的“产品改进 / Improvements”页面包含：

- 待查看、待补充、相似问题、已纳入、已完成和暂缓筛选；
- 提交人、提交时间、功能范围和影响程度；
- Codex 诊断摘要与建议；
- “请提交人补充”“标记为相似问题”“暂不安排”“纳入改进”等自然语言判断；
- 已纳入反馈与正式迭代任务的一对一关联；
- 正式任务完成后的关闭与状态回写。

同一条反馈只会生成一个正式迭代任务。重复点击“纳入改进”不会生成多份任务。

## Codex First 的分工

### `diagnose-cofound-feedback`

运行在提交人的 Codex：

1. 选择或新建一条明确反馈；
2. 领取一条诊断任务，防止同一条被多个会话同时处理；
3. 用非敏感样例复现；
4. 区分观察事实与推断；
5. 输出摘要、建议动作、检查、风险和待确认问题；
6. 完成后触发安全同步。

默认不修改代码。只有提交人明确要求，并且本地副本适合修改时，Codex 才可以做一次受限试修。试修只作为维护证据，不会自动合并、推送、发布或替换正式版本。

### `iterate-cofound-product`

仅运行在维护者工作区：

1. 接收已由维护者“纳入改进”的正式任务；
2. 在隔离的本地版本中修改；
3. 完成与风险相匹配的检查；
4. 把非技术结果返回网页等待人工审核；
5. 只有网页已明确批准时，才允许应用到主版本。

这两个 Skill 不互相冒充。反馈诊断不会绕过维护者直接更新团队正式版本。

## 飞书多维表格的定位

飞书在这里是企业内部的改进台账和跨电脑传递层，不是源码仓库，也不是 BP 原件的外部分发渠道。建议在现有 Cofound Base 中新增独立表：

`产品改进台账 / Product Improvement Register`

它与“项目文件索引”完全分开。产品反馈不得写进 BP 文件索引表。

面向维护者的主要字段包括：

- 问题标题、问题描述、期望结果；
- 提交人、提交时间、功能分类、影响程度；
- Codex 诊断摘要、建议处理动作、诊断检查、诊断风险、仍需补充信息；
- 试行修复状态、处理状态、维护者回复、处理人、处理时间；
- 应用版本、能力包版本。

系统还会保存协作键、顺序号和冻结上报内容等校验字段，用于去重、按序更新和读回验证。这些字段应放在维护视图末尾或专门的“同步审计”视图中，普通使用者无需理解或填写。

## 安全边界

允许同步：

- 用户在反馈页明确填写的内容；
- 当前显示名、提交时间、应用版本与能力包版本；
- Codex 输出的安全诊断摘要、建议、检查、风险和待确认问题；
- 维护状态、维护者回复和关联任务编号。

禁止同步：

- 本机路径、文件名、源码位置、命令、日志、报错堆栈；
- Git 分支、提交号、哈希、补丁或完整源码；
- 账号、令牌、验证码、密码、环境变量或认证细节；
- 原始 Codex 对话和提示词；
- BP 正文、财务数据、客户名称、合同、证据原文或其他项目敏感资料；
- 未经用户明确选择的附件和外部链接。

飞书同步采用用户身份、精确协作键查询、同键串行锁、顺序号检查和写后读回。遇到同键多记录、旧序号覆盖新序号、字段结构不符或读回不一致时会停止，而不是猜选一条继续写。

## 本地状态与飞书状态

业务状态和传输状态必须分开：

- 业务状态：待查看、待补充、相似问题、暂缓、已纳入、已完成；
- 诊断状态：等待 Codex、处理中、检查中、需要关注、已整理；
- 同步状态：待发送、已同步、发送失败。

“已同步”只表示安全摘要已经通过读回校验，不表示维护者已经同意。“发送失败”也不影响本机反馈继续存在。

## 启用飞书连接

代码安装后即可以只用本地反馈。要启用跨电脑同步，需要在现有 Cofound Base 中创建独立台账，并把精确表定位写入本机内部存储配置：

- `feedbackBaseToken`：可选；不填时使用现有 Cofound Base；
- `feedbackTableId`：必填；必须是已经确认的精确表 ID 或名称。

系统不会猜测表名，也不会在缺少配置时擅自创建表、字段或记录。配置完成后先执行只读结构检查；只有字段完整匹配，才允许发送或拉取。

## 与 Vercel 和 BP 数据的关系

- 本地 BP 管理、事实提取、投资分析和正式维护仍以本机 Cofound 为核心；
- 飞书负责内部原文件归档和本次产品反馈台账；
- Vercel 只负责被明确选择的外部项目分享；
- 产品反馈不会自动进入 Vercel，也不会把 BP 原件附带上传到飞书台账。

因此，团队反馈功能不会扩大外部分享面，也不会改变既有 BP 存储边界。
